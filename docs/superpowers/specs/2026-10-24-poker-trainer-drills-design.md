# Poker Trainer — Phase 2a: Quiz / Drill (Design)

Date: 2026-10-24
Builds on: `2026-10-24-poker-trainer-bot-play-design.md` (phase 1, merged).

## Purpose and scope

A drill mode in the same browser-only site. The player answers short situational questions and gets immediate feedback with a reason, an EV figure where one can be computed honestly, and a label saying how trustworthy the answer key is.

Phase 2 is split: **2a (this spec)** = drill framework + three drill types; **2b (later, separate spec)** = postflop spots, which have no trustworthy answer key without a solver.

### Drill types in 2a
1. **Pot odds / equity** — exact answers.
2. **Preflop by position** — approximate answers (guideline, not GTO).
3. **Heads-up push/fold** — exact within heads-up (computed Nash equilibrium, simulated equities).

### Assumptions (confirm or correct)
- Hold'em no-limit, play money, no backend, no accounts; results stored in the browser like phase 1.
- Multi-way push/fold, postflop, importing the user's own range files, and generating drills from the user's mistakes in phase 1 are **out of scope** for 2a.
- An answer-source interface (`RangeSource`) exists so a user-supplied range source can be added later, but no import UI is built now.

### Success criteria
- All three drill types can be played in sets of 10 questions with feedback after every answer.
- Every feedback panel shows a certainty label ("Exact" or "Guideline") that matches how the key was produced.
- EV is shown only where computed exactly; never invented.
- Results persist across reloads; questions the player misses often appear more often.
- Existing phase 1 history and backups keep working after the database upgrade.

## Architecture

```
src/drill/
  types.ts            Question, Answer, Grade, DrillModule
  modules/
    oddsDrill.ts
    preflopDrill.ts
    pushFoldDrill.ts
  data/pushFold.json  generated by scripts/build-pushfold.ts (committed)
  rangeSource.ts      RangeSource interface + built-in implementation
  runner.ts           builds a 10-question set, weights by past mistakes
  progress.ts         summarises stored results
scripts/build-pushfold.ts   one-off build script computing the Nash tables
src/ui/DrillPage.tsx
```

Layering: `drill` depends on `engine` and `coach` (pot odds, preflop advice). It does not depend on `bots` or `session`. `ui` calls `drill`. `store` gains one object store.

### Module interface
```
DrillModule {
  id: 'odds' | 'preflop' | 'pushfold'
  levels: number
  generate(rng, level): Question          // pure, deterministic for a given rng state
  grade(question, answer): Grade
}
Grade {
  correct: boolean
  borderline: boolean                     // either neighbouring answer acceptable
  explanation: string
  certainty: 'exact' | 'approximate'
  ev?: { chosen: number; best: number; unit: 'chips' | 'bb' }
}
```
A question carries a `key` (scenario signature such as `preflop:BTN:none:AJo`) used for progress tracking and weighting.

## Drill types

### 1. Pot odds / equity (exact)
- Level 1: given pot and bet, choose the required equity (4 options).
- Level 2: given a number of outs on the flop or turn, estimate equity (rule of 2 and 4); an answer within ±5 percentage points of the exact value is correct.
- Level 3: outs + pot + bet, choose call or fold, counting **only the next card** (outs over 47 unseen on the flop, 46 on the turn). Using two-card odds against a single bet would teach chasing draws, so the prompt says "count only the next card".
- Level 2 uses 1–12 outs: above that the rule of 4 drifts more than the 5-point tolerance.
- Exact equity is computed by counting outs against the unseen cards (one card to come on the turn; two cards to come on the flop), not by simulating against a random hand, because a player facing a bet usually has a stronger opponent than a random one.
- EV(call) = equity × pot − (1 − equity) × call; EV(fold) = 0. The panel states that later betting rounds are not included.

### 2. Preflop by position (approximate)
- Random hand, position (EP, MP, CO, BTN, SB, BB) and situation (nobody has raised / facing a raise); answer fold, call or raise. The big blind is only asked when facing a raise (with no raise it simply checks). Stack depth is not shown; the key assumes deep stacks (about 100bb).
- The key is `coach/preflopAdvice` (the same table as the in-game hint). A hand whose Chen score is within 1 of the relevant threshold is **borderline**: both adjacent answers are accepted.
- No EV is shown. Certainty is `approximate` and the panel says "Guideline, not GTO".

### 3. Heads-up push/fold (exact within heads-up)
- Small blind: stack 2–15bb (whole numbers), choose push or fold. Big blind: facing a push of that stack, choose call or fold.
- `scripts/build-pushfold.ts` builds `data/pushFold.json`: a 169×169 hand-class equity matrix by Monte Carlo (fixed seed), then, for each stack, iterates best responses between the pushing and calling ranges (weighted by combinations: 6 pairs, 4 suited, 12 offsuit) until the ranges stop changing, and stores the push range, the call range and per-hand EVs in bb.
- EV conventions (bb, relative to the start of the hand): SB fold = −0.5; SB push = (1 − c) × 1 + c × (2 × eq × S − S), where c = probability the BB calls, eq = equity when called, S = effective stack in bb; BB fold = −1.
- Because the equity matrix is simulated (about ±1%), an answer is correct when its EV is within 0.1bb of the best EV (borderline when the difference is below that). The panel states this and that the result is heads-up only.

## UI

`DrillPage`: choose type and level → set of 10 questions → question card (existing `CardView`) → answer buttons → feedback panel (correct / incorrect / borderline, short reason, EV table when present, certainty badge) → next → end-of-set summary (score, accuracy by type). Entry point added to the lobby.

## Data and persistence

- IndexedDB version 2 adds object store `drillResults` (key `id`): `{ id, type, level, key, correct, borderline, evLoss?, timestamp }`. The upgrade only creates the new store; `hands` and `sessions` are untouched.
- `progress.ts` computes accuracy by type and by `key` from stored results; it is derived, not stored.
- Backup file version becomes 2 and includes `drillResults`; importing a version 1 file still works (no drill results).
- Weighting: the runner generates 5 candidate questions per slot and picks one with probability proportional to `1 + 3 × missRate(key)` (miss rate 0 for unseen keys). Modules are unaware of this.

## Error handling

- Result write fails: the drill continues, the panel shows "this answer was not saved" (same behaviour as phase 1).
- A stored drill result that does not parse is skipped; it never breaks the progress view or a set.
- Backup import validates drill results before writing anything (all or nothing), as phase 1 does for hands.
- `pushFold.json` is bundled at build time; a missing stack row in the data is a build-script test failure, not a runtime case.

## Testing

- Odds: exact outs equity values (e.g. 9 outs on the flop ≈ 35.0% by the river; 9 outs on the turn ≈ 19.6%), the ±5-point tolerance boundary, call/fold sign of EV.
- Preflop: grading for clear fold, clear raise, and both sides of a borderline hand; certainty label is `approximate`; no `ev` field.
- Push/fold: AA and KK always push at every stack; push range never grows as the stack grows; at 2bb the SB pushes nearly every hand; EV(push) for AA exceeds EV(fold); script output is deterministic for a fixed seed.
- Generators: same seed gives the same question; every generated question grades without error for every possible answer (property test over many seeds).
- Runner: weighting favours missed keys (statistical test with a fixed seed); a set has exactly 10 questions.
- Store: a version 1 database with saved hands upgrades to version 2 with all hands intact; version 1 backups import; bad drill results are rejected on import.
- UI: answering shows the feedback panel with the right certainty badge; borderline label appears for a borderline preflop hand; unsaved-answer warning appears when the write fails.
